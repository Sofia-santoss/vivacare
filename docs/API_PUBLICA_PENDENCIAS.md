## Pendências para testes reais

1. **Migration ledger/histórico:** reconciliar com DBA quais migrations foram aplicadas. O runner não deduz versões se o ledger está ausente e recusa `apply`; não registrar baseline sem validação formal.
2. **Migration 007:** confirmar `current_user`, membership da role de aplicação, owner/ACL de `usuario_setores` e estado validado da migration. Se 007 estiver pendente no histórico reconciliado, aplicá-la pela cadeia oficial. Não editar 007 nem conceder `SUPERUSER`/privilégios amplos.
3. **Perguntas NOTA:** NPS geral é campo separado 0–10; avaliação setorial é 1–5. A proposta de escalas classifica os prompts canônicos observados e bloqueia perguntas não classificadas. Aprovar a finalidade/faixa de qualquer prompt divergente antes da promoção.
4. **Turno/equipe:** a rota canônica salva a resposta sem turno/escala correspondente e registra a ausência de equipe. O schema atual com `turno_id NOT NULL` ainda não suporta esse fluxo; a alteração está apenas na proposta de escalas.
5. **Rate limit:** configuracao aprovada: `PUBLIC_SURVEY_IP_LIMIT=60` e `PUBLIC_SURVEY_IP_WINDOW_SECONDS=60`. Pesquisa e Ouvidoria usam contadores HMAC independentes; codigos de pesquisa compartilham o bucket da familia de pesquisa. `AUTH_LOGIN_THROTTLE_SECRET` deve permanecer estavel entre instancias; `PUBLIC_SURVEY_FINGERPRINT_SECRET` e separado para idempotencia. Atras de proxy, `TRUSTED_PROXY_IPS` lista os IPs exatos confiaveis. A limpeza usa exclusivamente `DB_MAINT_USER` e `DB_MAINT_PASSWORD`, validados contra membership e privilegios MAINT.

**Agendamento da limpeza no Render:** a dupla informou que o backend será hospedado no Render. Crie um serviço **Cron Job** no Dashboard usando o mesmo repositório/branch; configure root directory `backend`, build command `npm ci && npm run build`, comando `npm run db:cleanup:public-limits` e agenda `0 * * * *` (a cada hora, no minuto zero, em UTC). O projeto não cria esse serviço automaticamente, e nenhum Cron Job foi criado nesta sessão. Configure no secret manager do job `NODE_ENV=production`, `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_SSL=true`, `DB_MAINT_USER`, `DB_MAINT_PASSWORD` e, se necessário, `DB_SSL_CA`; configure também `PUBLIC_SURVEY_IP_WINDOW_SECONDS=60`. Não configure `DB_USER` nem `DB_PASSWORD` nesse job. Antes de habilitar o job, confirme com a DBA que as tabelas de limites existem e que a role MAINT tem somente os privilégios previstos. A agenda do Render usa UTC: https://render.com/docs/cronjobs.

**Envio de convites pelo Gmail:** o backend tem adaptador SMTP e validação de configuração. Use como `SMTP_USER` a conta Google que efetivamente gerou a senha de app; `USER_INVITE_FROM` deve usar essa mesma conta. Configure `SMTP_HOST=smtp.gmail.com`, `SMTP_PORT=587`, `SMTP_SECURE=false` e guarde `SMTP_PASSWORD` somente nos segredos do Render. Confirme o endereço atualmente configurado no serviço antes de orientar a equipe; não copie credenciais para GitHub ou conversa. A [ajuda oficial do Google sobre senhas de app](https://support.google.com/mail/answer/185833?hl=pt-BR) explica os requisitos.
6. **Ouvidoria independente:** a proposta de escalas valida `manifestacoes.resposta_id IS NULL` e retira o índice legado. Se houver manifestação antiga ligada a resposta, a validação falha sem apagar dados e precisa de decisão antes de promover.
7. **Proposta de escalas:** comparar novamente o inventário real, validar em PostgreSQL descartável, aprovar as decisões acima e só então promover com a próxima versão livre, como migration oficial imutável. A proposta não é carregada pelo runner.

O frontend usa o POST público em `/api/public/pesquisas/:codigo/respostas`; a rota usa o repositório novo que aceita ausência de turno/equipe. Esse fluxo depende dos objetos da proposta 009; a execução do teste geral de migrations (`npm run test:db`) não substitui `npm run test:surveys:db`. O último reseta o schema `public`; deve usar um banco local novo, descartável e exclusivo, com `VIVACARE_SURVEYS_TEST_DB_HOST=127.0.0.1`, `VIVACARE_SURVEYS_TEST_DB_NAME=vivacare_surveys_test`, `NODE_ENV=test` e `VIVACARE_SURVEYS_TEST_DB_DISPOSABLE=YES`. Configure também `VIVACARE_SURVEYS_TEST_DB_PORT`, `..._USER`, `..._PASSWORD`, `..._APP_USER`, `..._APP_PASSWORD`, `..._MAINT_USER` e `..._MAINT_PASSWORD`. As três identidades devem ser distintas; SETUP deve ser dono do banco e conseguir recriar o schema, mas não pode ser SUPERUSER. Não reutilize o banco do teste `test:db`. O comando deve ser executado de `backend/` depois de conferir `pg_dump --version` igual a 18.4. Após a execução, o schema fica preparado no banco e ele pode ser descartado se foi criado só para o teste. Ouvidoria permanece em endpoint e tabelas próprios, sem vínculo com resposta anônima de pesquisa.

As rotas protegidas de gestão de pesquisas e perguntas estão implementadas em `/api/pesquisas` e `/api/perguntas`. Pesquisas são criadas inativas; `ADMIN_SETOR` administra perguntas apenas nas pesquisas dos setores associados. Novas perguntas `NOTA` são recusadas até a migration de escalas ser promovida e as faixas serem configuradas. Perguntas `OPCAO` continuam aceitando texto livre, pois o schema ainda não armazena uma lista de opções.
